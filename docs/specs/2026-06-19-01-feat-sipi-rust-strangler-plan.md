# SIPI: Rust rewrite via strangler fig (in-process FFI, socket-last)

> **➜ ACTIVE PLAN SPLIT OUT (2026-06-23):** the forward execution plan for the remaining Phase C cutover — the **differential-parity strategy** (C++ retained as a *live oracle*; deploy only after **C + T + Docs**; transport delete dead-last), the coverage-gap inventory, the differential-harness design, and the open decisions — now lives in **[`02-feat-sipi-cutover-differential-parity-plan.md`](2026-06-19-02-feat-sipi-cutover-differential-parity-plan.md)**. **This file (`01`) is the foundational record**: strategy, locked architectural decisions, completed Phases 0/A/B/B-L + the Phase C foundation, the seam ABI, and the full session history. The "prod canary as the Phase C exit gate" framing below is **superseded** by `02` §1.

Rewrite SIPI from C++ to Rust incrementally, using a strangler fig in which a Rust HTTP shell takes over the listening socket once a **narrow C FFI seam** can drive the existing C++ image engine. End-state per [ADR-0013](https://github.com/dasch-swiss/sipi/blob/main/docs/adr/0013-shttps-as-internal-module.md): the whole of SIPI in Rust, `shttps/` first, **Kakadu permanently behind FFI**.

This plan supersedes the Phase 0–4 sketch in the [*Sipi: Incremental Rust rewrite (strangler fig via FFI)*](https://linear.app/dasch/project/sipi-incremental-rust-rewrite-strangler-fig-via-ffi-ba50b17b032a) project description (the 2026-03-03 feasibility analysis). That sketch predates both the [SIPI Modularization](https://linear.app/dasch/project/sipi-modularization-3e0cc2fd19f2) progress and the central finding below.

> **2026-06-20 revision.** After landing the first Phase B slice (the seam header + `sipi_serve_file`) and probing `sipi_preflight`, two things changed. (1) The seam shape is now **locked as-built** — it carries two body-delivery modes (`send_file` for known length, `write` for unknown), and the engine uses a `decide`/`apply`/`guard` internal pattern. (2) Phase B is **re-sequenced**: the **Lua-free engine FFI** (`serve_file`/`serve_image`/metrics) is clean and comes first; the **Lua FFI** (`preflight`/`run_lua_route`/`init`) is split into a new **Phase B-L** that does the `request_context` Lua↔`Connection` decoupling *first* — the original plan put `request_context` in Phase C while scheduling `preflight` in Phase B, a backwards dependency the old text half-admitted. See **§Session handoff** and **§Phase B / §Phase B-L**.

> **2026-06-21 revision.** **Phase B is complete and merged** (PR [#688](https://github.com/dasch-swiss/sipi/pull/688)). `sipi_metrics_snapshot` landed; the `decide`/`apply`/`guard` pattern's producer was renamed **`decide_serve_*` → `build_*_response`** (it builds the concrete `ServeResponse`, it doesn't pick an intent) — the pattern is now **build → apply → guard**. All Phase B commits are typed `refactor`/`build`/`test` (seam work delivers no end-user value until the Phase C cutover; [[commit_type_matches_subject]]). Next is **Phase B-L**. The text below still says `decide_*` in the historical/reference write-ups — read it as `build_*_response`.

> **2026-06-21 revision (Phase B-L preflight MERGED).** Phase B-L is complete for its scope and **merged to `main`** via PR [#689](https://github.com/dasch-swiss/sipi/pull/689) (rebase commits `2ce86df` request_context / `94e16af` carve / `dd573a2` relocation / `df02246` preflight; pre-rebase branch SHAs `53a612a`/`aebcbb1`/`6754822`/`9c11687`), four slices, full unit+approval+e2e + 3-platform CI + sanitizer green. **As-built seam change:** preflight takes the **full request as an opaque `SipiRequestContext`** (= C++ `shttps::RequestContext`), not a bare cookie — Lua reads any field via `server.*` (the narrow shape broke JWT-via-`Authorization` auth, and the full handle keeps existing user Lua scripts running unchanged). **`sipi_run_lua_route` and the complete `sipi_init` moved to Phase C** (the shell layer owns route dispatch + the config install; doing them in B-L would invert layering or be dead code). A new **Phase T** (between C and D+) makes `pre_flight` / `file_pre_flight` a Rust **trait** (SIPI-as-library). See **§Session handoff** and **§Phase B-L / §Phase C / §Phase T**.

> **2026-07-13 revision (Step 10 crash-reporting cutover MERGED).** `02`'s step 10 (Item 3, DEV-6659) merged to `main` via [sipi#718](https://github.com/dasch-swiss/sipi/pull/718): `sentry-native` dropped entirely; the Rust `sentry` crate owns panics + handled image-decode errors across a new `SipiImageErrorReport` FFI seam; `sentry-rust-minidump` captures native crashes out-of-process, verified live against a real SIGSEGV inside the actual distroless container. Getting asan-ubsan CI green surfaced **4 distinct, confirmed ASan thread-registry false positives** (not real bugs) — Kakadu's encoder thread pool, tokio's runtime-teardown join, `ureq`'s DNS-resolver thread in the `health` verb, tokio's blocking-pool keep-alive retirement — each independently root-caused and fixed. The PR's ~28-commit investigative trail was collapsed post-merge into 6 clean commits and force-pushed onto `main` in place of the original merge (Ivan's call, same verified tree). Full as-built detail lives in `02` §8's Step 10 section. **Remaining before the §9 deploy gate:** Phase 5 (debug-symbol upload check) and Phase 6 (staging `kill -SEGV`, operator-gated).

## The central finding

The feasibility analysis named `shttps::Connection` (43 methods, 15 consumers) "the hardest coupling." Grounding the current code shows the coupling that actually blocks the strangler is far narrower:

- **The image-write path collapses to one call.** All codec wrappers — JPEG `HtmlBuffer`, J2k `J2kHttpStream`, PNG `png_io_context`, **and TIFF** (the prose originally under-counted — 4 codecs, not 3) — converged on `conobj->sendAndFlush(buf, n)`. The rich Connection API (cookies, uploads, chunked modes) is used by *handler orchestration*, not by the image engine. **(Removed in Phase A.)**
- **`SipiImage` carried a `shttps::Connection *conobj`** purely to reach that one call; the `"HTTP"` magic-string sentinel routed writes to it. **(Removed in Phase A.)**
- **The IIIF dispatch is clean.** `iiif_handler` parses the URL via the pure state machine `handlers::iiif_handler::parse_iiif_uri` and switches on request type.
- **`SipiHttpServer` still inherits `shttps::Server`**; composition-over-inheritance (DEV-6441) has not landed, but the cutover **deletes** `shttps::Server`, dissolving the inheritance rather than refactoring it.

**Consequence for "shortest path":** the only *hard* modularization prerequisite from the ~97-issue backlog was replacing that one `sendAndFlush` coupling with a caller-supplied sink — exactly [ADR-0006](https://github.com/dasch-swiss/sipi/blob/main/docs/adr/0006-format-handler-api-modernization.md)'s `OutputSink` (done). Once the engine writes bytes to an opaque callback, it has zero `shttps` dependency and Rust can own the socket. Everything else in the backlog is either absorbed into a later Rust slice or is independent C++ cleanup that never gates the strangler.

## Architectural decisions (locked)

1. **In-process FFI, single binary.** Rust shell (axum + tokio) over the C++ image engine via a C ABI. One deploy artifact. Rejected: out-of-process proxy (two artifacts, double running cost, Kakadu still FFI); pure-Rust engine first (Kakadu has no Rust equivalent).
2. **Socket-last cutover.** C++ keeps the socket until the narrow FFI seam exists; Rust takes it in one cutover. Rejected: socket-first via a ~43-method `Connection` shim — a throwaway bridge that violates "no shims for code that can just change." We cut the *narrow, durable* seam (params + callbacks), not the wide one.
3. **Phase A was the only hard modularization gate.** We did not finish modularization before starting; we pulled exactly the `OutputSink` slice.
4. **Lua stays C++ through the cutover, reached by FFI — but its `Connection` dependency is cut *before* the Lua FFI, in Phase B-L (not Phase C).** Reimplementing the ~60-function mlua surface is deferred to D+. The preflight hook, configured Lua routes, and the init script run in the existing C++ `LuaServer` behind FFI entry points, fed by a buffered **`request_context`** instead of a live socket. **The `request_context` decoupling is a prerequisite for clean Lua FFI** (`LuaServer` currently links against `Connection`), so it moves up from Phase C into Phase B-L. The carved `shttps/{lua,lua_sqlite,jwt}` is renamed to `src/lua_runtime/` at the Phase C cutover.
5. **Build stays Bazel-native.** The Rust shell lives in the existing Bazel graph via `rules_rust` + a new production Crate Universe manifest (separate from `//test/e2e-rust`). No standalone cargo workspace; no `bazel`/`nix build` outside `just bazel-*`. `rules_foreign_cc` is eliminated — every C++ dep incl. Kakadu is a native `cc_library` ([ADR-0015](https://github.com/dasch-swiss/sipi/blob/main/docs/adr/0015-native-cc_library-over-foreign_cc.md), landed), so a `cc_library` links cleanly into a `rust_binary` (modulemaps present, no foreign_cc friction).
6. **Behaviour preservation is the safety net.** Approval tests (image bytes) stay green throughout A and B because the engine is untouched. The existing Rust e2e suite (`test/e2e-rust`, reqwest) is the parity harness for the Phase C cutover.
7. **The seam carries two body-delivery modes; framing is the transport's call, never the engine's** *(new, as-built)*. `send_file(path, offset, length)` delivers a **known-length** body — the transport frames it with `Content-Length` (and may use zero-copy `sendfile(2)`, landing DEV-6080). `write(data, len)` delivers an **unknown-length** body (the image encoder, whose size isn't known until encode finishes) — the transport frames it chunked. The engine declares *which*; the transport picks the wire framing appropriate to the negotiated HTTP version (Content-Length / HTTP-2 DATA frames / chunked). Chunked is **never** hard-coded in the seam. Known-size downloads keep Content-Length — the shape browsers/media players need for size + seeking.
8. **Engine-internal misuse-resistant pattern; no exception crosses the boundary** *(new, as-built; renamed `decide_*`→`build_*_response` at the Phase B merge)*. Each **response-emitting** FFI entry is `build_*_response` (pure of the transport → `std::expected<ServeResponse, SipiStatus>`, unit-testable without a socket; every failure-prone step runs here, *before* the response is committed, so failures are clean status codes — it builds the concrete response, it doesn't choose an intent) → `apply` (the single place that touches the C callbacks; dispatches a `std::variant` body, so exactly one body is emitted by construction) → all wrapped in `sipi_guard` (catch-all → 500). **Non-emitting entries drive no response sink, so they skip `build`/`apply` and are `sipi_guard`-only** — `sipi_metrics_snapshot` (a pure singleton read; as-built) and, in B-L, `sipi_init`. **`sipi_guard` contains C++ *exceptions*, not *crashes*:** a codec segfault on a malformed image (`SIGSEGV`/`SIGBUS`/`SIGFPE`) is a hardware fault `catch(...)` cannot catch and will take the (single-process) server down. That residual risk is the image-engine-hardening backlog (category D below): the strangler does not *prevent* the crash, but Phase C does *report* it — an out-of-process minidump reporter replaces `sentry-native` (see Phase C §Crash & error reporting).

9. **The Phase C Rust shell ships as a library + a thin binary, extensible via traits (future)** *(new, 2026-06-21)*. The shell is a `sipi` **library crate** (`lib.rs`, owns the axum app / routing / FFI / config / OTel and statically links the C++ engine) plus a **thin default `rust_binary`** (`main.rs`, just calls `sipi::run()`). This is what lets SIPI be consumed **as a dependency**: a downstream user crate can own `main`, depend on `sipi`, and inject its own behaviour. The request-shaping policy Lua owns today (the preflight hook, configured custom routes) becomes a Rust **trait** in D+ whose **default impl wraps the C++ Lua FFI** (`sipi_preflight` / `sipi_run_lua_route`); a user crate supplies its own impl without forking SIPI. This needs **no B-L / Phase-C seam change** — preflight is already a discrete, orchestrated step with a pure data contract (a permission-type enum + an *open* key/value map, decision #8's `build_preflight`), decoupled from the serve path (`sipi_serve_image` never calls preflight; the shell threads its outputs in as inputs). The only forward-looking cost is shipping the shell as lib+bin (mechanical, additive) and modelling `build_preflight`'s return as a clean value type (already planned). **Scope: preflight + custom routes only**, never config parsing — the `config.*` surface stays config ([[lua_for_request_shaping_only]]).

## Phase B — Lua-free engine FFI core

**Goal:** expose the IIIF **image** pipeline + raw file download as a stable C ABI, decoupled from `shttps::Connection` on read and write, depending on **no Lua** (and therefore on no `transport`). Prove it by routing the *existing C++ server* through it. `//src/ffi:sipi_ffi` depends only on `//src/shttps/util` (generic MIME/util) + the image engine — it is transport-free.

**Tracked by [DEV-6658](https://linear.app/dasch/issue/DEV-6658)** (blocked by Phase A).

### The seam, as built (`src/ffi/sipi_ffi.h`, `extern "C"`)

The C ABI is the durable, Rust-/bindgen-consumable contract. The response is **streamed via callbacks** (status + header + body + cancel), never a fixed result struct, so it can express Range/206, repeated `Set-Cookie`, `Retry-After`, `Content-Disposition`, etc. Two body-delivery callbacks (decision #7): `send_file` (known length → Content-Length) and `write` (unknown length → chunked).

```c
/* Body bytes, forward-only, UNKNOWN length (image encoder) → transport frames chunked. */
typedef int  (*SipiWriteFn)    (void* ctx, const uint8_t* data, size_t len);
/* KNOWN-length file region [offset, offset+length) → transport frames Content-Length (zero-copy where it can). */
typedef int  (*SipiSendFileFn) (void* ctx, const char* path, uint64_t offset, uint64_t length);
typedef void (*SipiHeaderFn)   (void* ctx, const char* name, const char* value);  /* one call per line; Set-Cookie may repeat */
typedef void (*SipiStatusFn)   (void* ctx, int status);
typedef int  (*SipiCancelledFn)(void* ctx);   /* 1 = client gone / timed out → abort + unlink partial cache */

typedef struct {              /* Rust-owned (or, in the Phase B parity path, Connection-owned) response sink */
  void*           ctx;
  SipiStatusFn    set_status;
  SipiHeaderFn    add_header;
  SipiWriteFn     write;       /* unknown-length / chunked */
  SipiSendFileFn  send_file;   /* known-length / Content-Length */
  SipiCancelledFn cancelled;
} SipiResponse;

/* region/size/rotation/quality/format, flattened (typed enums mirror SipiRegion::CoordType,
   SipiSize::SizeType, SipiQualityFormat::QualityType/FormatType) so the seam carries no
   iiifparser class layout (those types move to Rust in D+ without changing this ABI). */
typedef struct { /* SipiIiifParams — see header for the enum members + fields */ } SipiIiifParams;

typedef struct {
  const char* resolved_path;    /* image-root-validated absolute path (validation owned by the Rust edge) */
  const char* prefix;           /* IIIF prefix — canonical-URL + cache key */
  const char* identifier;       /* IIIF identifier — canonical-URL `id` + cache key */
  const char* client_ip;        /* rate-limit key — XFF-resolved at the Rust edge (DEV-6072) */
  SipiIiifParams params;
  const char* restricted_size;  /* preflight `restrict` downscale, or NULL */
  const char* watermark_path;   /* preflight `restrict` watermark, or NULL */
  const char* forwarded_proto;  /* X-Forwarded-Proto → canonical-URL / redirect scheme */
  const char* forwarded_host;   /* X-Forwarded-Host  → canonical-URL `id` */
} SipiServeRequest;

/* Returns 0 / an HTTP status code (404/400/500) on a pre-commit failure; NEVER lets a C++
   exception cross the boundary. SIPI_FFI_NODISCARD = [[nodiscard]] under C++, empty under C. */
SIPI_FFI_NODISCARD int sipi_serve_image(const SipiServeRequest* req, const SipiResponse* resp);   /* Phase B, NEXT */
SIPI_FFI_NODISCARD int sipi_serve_file (const char* resolved_path, const char* range /*or NULL*/, const SipiResponse* resp); /* Phase B — DONE */
SIPI_FFI_NODISCARD int sipi_metrics_snapshot(SipiMetricsSnapshot* out);   /* Phase B — engine counters → Rust OTel meter */

/* --- Phase B-L (Lua preflight) — DONE --- */
typedef enum { SIPI_ALLOW, SIPI_LOGIN, SIPI_CLICKTHROUGH, SIPI_KIOSK, SIPI_EXTERNAL, SIPI_RESTRICT, SIPI_DENY } SipiPermType;
typedef void (*SipiKVFn)(void* ctx, const char* key, const char* value);
typedef struct SipiRequestContext SipiRequestContext;  /* opaque: the whole request (= C++ shttps::RequestContext) — Lua reads any field via server.* */
SIPI_FFI_NODISCARD int sipi_preflight(const char* prefix, const char* identifier, SipiRequestContext* ctx,
                                      SipiPermType* type, SipiKVFn emit_kv, void* kv_ctx);  /* IIIF pre_flight */
SIPI_FFI_NODISCARD int sipi_file_preflight(const char* filepath, SipiRequestContext* ctx,
                                      SipiPermType* type, SipiKVFn emit_kv, void* kv_ctx);  /* /file file_pre_flight (audio/video/PDF) */
/* --- Phase C --- */
SIPI_FFI_NODISCARD int sipi_run_lua_route(const char* script, SipiRequestContext* ctx, const SipiResponse* resp); /* moved B-L → C (shell owns route dispatch) */
SIPI_FFI_NODISCARD int sipi_init(const char* lua_config_path, const SipiServerConfig* overrides); /* C++ parses Lua config; struct = CLI/env overrides only; moved B-L → C */
SIPI_FFI_NODISCARD int sipi_cli_main(int argc, char** argv);   /* hands argv verbatim to CLI11; returns the exit code */
/* /health + /favicon.ico are Rust-native — no FFI. SipiServerConfig/SipiMetricsSnapshot are opaque until their slice. */
```

### Engine-internal C++ API (`src/ffi/serve_response.{h,cpp}` — NOT the C ABI)

The C ABI is dumb on purpose; this layer drives it correctly by construction (decision #8):

```cpp
enum class SipiStatus : int { Ok = 0, BadRequest = 400, NotFound = 404, InternalError = 500 };

struct FileBody   { std::string path; std::uint64_t offset, length; };  // known length → Content-Length
struct EmptyBody  {};                                                   // HEAD / 0-length
struct StreamProducer { virtual ~StreamProducer() = default; virtual int produce(const StreamSink&) = 0; };
struct StreamBody { std::unique_ptr<StreamProducer> producer; };        // unknown length → chunked
using  Body = std::variant<FileBody, EmptyBody, StreamBody>;            // exactly one, by construction

struct ServeResponse { int http_status; std::vector<std::pair<std::string,std::string>> headers; Body body; };

std::expected<ServeResponse, SipiStatus> decide_serve_file(const char* resolved_path, const char* range); // pure of transport
void apply(ServeResponse&&, const SipiResponse&);   // the ONLY place that touches the C callbacks
template <class F> int sipi_guard(F&& f) noexcept { try { return f(); } catch (...) { return 500; } }
```
`StreamBody` uses `unique_ptr<StreamProducer>` (not `std::move_only_function` — unavailable in this libc++, [[sipi_no_move_only_function]]) and stays decoupled from `SipiImage`. `sipi_serve_file` = `sipi_guard([&]{ auto d = decide_serve_file(...); if (!d) return int(d.error()); apply(std::move(*d), *resp); return 0; })`.

### sipi_serve_file — ✅ DONE

Raw `/file` passthrough, Range/206, **no decode**. `build_file_response` does `access`(404) → `stat`(500) → MIME (`shttps::Parsing::getBestFileMimetype`) → parse + **clamp** Range → `FileBody` (or `EmptyBody`). `apply` sets status + headers then calls `resp.send_file` → Content-Length framing (the parity adapter `conn_send_file` calls `Connection::sendFile`, which streams without buffering). Path-traversal validation (R1/R2) and the identifier-derived `Content-Disposition` stay **caller-side** at the boundary. **Content-Range is clamped to the delivered length** so it can never diverge from Content-Length (an RFC-correctness fix over the legacy handler). Parity routed through `serve_file_download`; e2e covers Range/206 + Content-Length.

### sipi_serve_image — ✅ DONE (PR #688)

Done as described below (the original design held). serve_iiif keeps preflight +
path validation, flattens the parsed IIIF params into `SipiServeRequest`, and
calls `::sipi_serve_image`; `build_image_response` reconstructs the typed params,
runs admission + canonical URL + decode/transform pre-commit, and returns a
`FileBody` (passthrough/cache-hit) or a `StreamBody` (encode-only producer with
the DEV-6660 integrity guard). Required the unplanned `//src:engine` carve first
(see §Session handoff). Parity: approval byte-identical + 23 e2e + 21 unit green.
The original design write-up follows for reference.

Extract the IIIF decode pipeline from `serve_iiif` (the ~700-line function, `src/SipiHttpServer.cpp`) behind `sipi_serve_image`, same `decide`/`apply`/`guard` shape:

- **`decide_serve_image`** runs, all **pre-commit** (so failures are clean status codes / 503): parse params → resolve canonical URL → admission: rate-limit (`SipiRateLimiter`), cache lookup (`SipiCache`), memory-budget (`SipiMemoryBudget`) → then **decode → rotate → convertToIcc → watermark** (the expensive, failure-prone steps). It returns:
  - a **`FileBody`** for a **cache hit** or a **direct passthrough** (full region + full size + no rotation/watermark + same format + DEFAULT quality → `sendFile` the cache/original); or
  - a **`StreamBody`** whose `produce` runs **only the encode** (`img.write(fmt, sink, params)` into a `TeeSink{ socket, cachefile }`), the rarely-failing tail. The decoded `SipiImage` is captured (by move) in the concrete `StreamProducer`.
- **`apply`** commits status + headers, then `send_file` (FileBody) or `produce` (StreamBody, chunked via `write`).
- **Cache tee + the DEV-6660 integrity guard** live inside `produce` (reuse Phase A's `TeeSink`; verify written size vs streamed bytes before `cache->add`; skip truncated / zero-byte HEAD files).
- **Cancellation:** `produce` polls `sink.cancelled()` between encode chunks (mirrors `peerConnected()` at `SipiHttpServer.cpp:1865,1902,1927,1953,1985`); the decode stages in `decide` poll it too — abort + unlink partial cache.
- **The parity adapter must implement `write`** (currently `nullptr`): `conn_write` needs a **one-time** `setChunkedTransfer()` before the first chunk (`Connection::setChunkedTransfer` throws once the header is sent, so it can't be called per-chunk). Wire this when serve_image lands.
- **No Lua:** `serve_iiif` keeps its existing **inline** preflight (`call_iiif_preflight`) and passes the resolved `infile` + `restricted_size` + `watermark_path` into `sipi_serve_image`. Preflight becomes an FFI call only in Phase B-L.
- **Hot-path benchmark required** (CLAUDE.md rule): a `process`/`encode` microbench before/after.

### sipi_metrics_snapshot — ✅ DONE (PR #688)

Snapshots the `Sipi::observability::Metrics` singleton counters/gauges into a flat `SipiMetricsSnapshot` (`src/ffi/metrics_snapshot.{h,cpp}`: uint64 monotonic counters, int64 gauges — signed for the `-1`=unlimited cache-size limit) for the Phase C Rust OTel meter. Reads under `sipi_guard`; **no decide/apply split** (no response sink, no fallible pre-commit step). The three `rate_limit_decisions_total` children (allowed/rejected/shadow_rejected) became cached `Counter&` members on `Metrics` (mirroring `decode_memory_*`), so the snapshot is a pure read and `serve_image.cpp`'s admission path dropped its per-request `Family::Add` lookups. Histograms (`request_duration_seconds`, `decode_memory_estimate_bytes`) + `build_info` are deliberately omitted (OTel records histograms natively; version/commit are resource attrs) — the inclusion rule is documented in the header. The C++ Prometheus `metrics_handler` stays until the Phase C cutover (then retired; OTLP-only).

### FFI contracts (load-bearing — set in Phase B)

- **No C++ exception crosses the boundary.** `sipi_guard` wraps every entry (`SipiImageError`, `SipiSizeError`, `std::bad_alloc`, `std::exception`, the bare-enum `OUTPUT_WRITE_FAIL`, libjpeg/libpng `setjmp`/`longjmp` aborts kept *inside* the codec's own C frames). A throw into Rust is UB — forbidden. **Crashes are out of scope** (decision #8).
- **Ownership & lifetime.** All `const char*` / struct inputs are caller-owned and outlive the (blocking) call; the engine copies anything it retains. The response is emitted only through `SipiResponse` callbacks — no engine-owned buffer handed back to free.
- **Validation ownership.** The **edge** (Rust in C; the C++ caller in the B parity path) resolves + validates the path (image-root containment + `..`/`%2e` rejection — `contains_traversal` / `realpath`) and passes an already-validated `resolved_path`; the FFI trusts it. Security checks stay at the boundary (DEV-6071/6072), not duplicated behind the FFI.
- **Whole-path thread-safety is a Phase B exit gate.** `sipi_serve_image`/`sipi_serve_file` must be reentrant under N `spawn_blocking` threads. `SipiCache` (mutex), `SipiRateLimiter` (scoped_lock), `SipiMemoryBudget` (lock-free) are safe; `serve_file` uses `gmtime_r` + a `static const std::regex` (safe for concurrent const match). The gate audits codec globals (Kakadu/libtiff error handlers), the `Metrics` singleton, and (in B-L) the per-request `LuaServer` VM + the shared `LuaSqlite` handle.

### Build / layering (as built + projected)

- `//src/ffi:sipi_ffi` — `cc_library`, `strip_include_prefix = "/src"` (headers as `#include "ffi/…"`), `copts = ["-fexceptions"]`. **Phase B deps: `//src/shttps/util` only** (the `getBestFileMimetype` MIME sniff) — transport-free. `serve_image` adds the image-engine deps (already in `:sipi_lib`).
- Wired into `//src:sipi_lib` so the existing server links the seam; the Phase-C `rust_binary` will link `:sipi_ffi` directly (`cc_import`/`deps`).
- **Phase B-L will add a dep on the Lua code.** Because `lua` is bundled with `transport` in `//src/shttps:shttps` and `LuaServer.o` references `Connection`, the Lua FFI can't be transport-free until `request_context` lands (hence B-L does the decoupling first).

### Parity proof (de-risks Phase C)

Route the existing `serve_iiif` / `serve_file_download` / `health_handler` through the new FFI internally (a `Connection`-wrapping `SipiResponse`). The C++ Prometheus `metrics_handler` is untouched in B (retired at the C cutover). Run the **full** approval + unit + e2e + smoke suite — behaviour unchanged, the seam exercised in production paths before Rust exists. Note: the comprehensive `range_requests.rs` e2e suite exercises the *separate* shttps docroot `/server/*` `file_handler` (generic framework code, **not** routed through the SIPI FFI — that would invert layering); the IIIF `/file` path gets its own Range/206 e2e tests in `server.rs`.

### Exit criteria (Phase B) — ✅ ALL MET (PR #688)

- `sipi_serve_image` + `sipi_serve_file` (+ `sipi_metrics_snapshot`) implemented and **called by the existing C++ server** (the parity proof — IIIF image + file-download/Range paths).

### Crash & error reporting (Sentry) — Rust owns it; `sentry-native` retired at the cutover

Today three Sentry concerns run through the C++ **`sentry-native` 0.9.0** SDK (inproc backend, curl transport, libbacktrace unwinder; `bazel/sentry.BUILD.bazel`): (1) **native crash capture** — SIGSEGV/SIGABRT signal handlers auto-installed by `sentry_init()` in `main` (`src/cli/sipi.cpp`); (2) a **`std::terminate` handler** reporting unhandled C++ exceptions as fatal events then `abort()`; (3) **structured handled-error events** — `capture_image_error` (`src/observability/sentry.{h,cpp}`), emitted from **8 call sites *inside the engine, behind the FFI*** (`src/ffi/serve_image.cpp` read/convert/write paths) with image dims/format/colorspace/ICC + IIIF URI + phase, plus the CLI convert path. Release = the build-stamped `BUILD_SCM_TAG`; `traces_sample_rate = 0.1`; config via `SIPI_SENTRY_{DSN,RELEASE,ENVIRONMENT}`.

**The gap the cutover must not open.** The pure-Rust [`sentry`](https://docs.rs/sentry) crate (v0.48.x) captures Rust panics, events, breadcrumbs and scopes, but Sentry confirms it [**cannot capture hard native crashes**](https://blog.sentry.io/debugging-a-segfault-in-rust/) (SIGSEGV/SIGBUS/SIGFPE) — exactly the codec faults on malformed images that are SIPI's primary crash risk (decision #8). `catch_unwind` and the panic hook only see unwinding panics, never signals from C/C++ UB. Crash *reporting* therefore needs a dedicated native path; it is **not** a free side effect of adopting the `sentry` crate. (The deprecated, archived FFI binding `sentry-contrib-native` — read-only since 2023-12-21, no linux-aarch64 CI — is **rejected**; its own author redirects to `crash-handler`.)

**Approach (recommended): Rust owns all of Sentry; drop `sentry-native` from the build** (the `@sentry` dep, `src/observability/sentry*.{h,cpp}`, the auto-signal-handlers, the `terminate` handler):
- **Panics + handled events** → the `sentry` crate, initialised once in Rust `main` (step 2 already routes "logging, Sentry, OTel" through Rust `main`). `release` = the stamped version, `environment` from `SIPI_SENTRY_ENVIRONMENT` (default `development`), `traces_sample_rate = 0.1`, `attach_stacktrace = true`, default panic integration; hold the `ClientInitGuard` for process life (blocking flush on CLI exit, drop-on-graceful-shutdown in server mode — ties to the SIGTERM drain). [`sentry-tracing`](https://docs.rs/sentry-tracing) plugs into the **same** `tracing-subscriber` the Observability section adds — one tracing pipeline feeds both Sentry and OTLP; PII hygiene shared (never `Authorization`/cookies/JWT).
- **Native codec crashes** → an **out-of-process** minidump reporter (the consensus-reliable model: the crashed address space is assumed corrupt, so the dump is written by a separate, intact process). Two options: (a) [**`sentry-rust-minidump`**](https://github.com/timfish/sentry-rust-minidump) (v0.16.x) — lowest-friction, re-spawns the same binary as the reporter and uploads minidumps to Sentry as attachments via the Rust SDK (single OCI image, no second artifact); or (b) raw [**`crash-handler` + `minidumper`**](https://github.com/EmbarkStudios/crash-handling) (Embark, the ecosystem standard) for full control. Both cover all three targets (darwin-aarch64, linux-x86_64, linux-aarch64). **One crash handler, not two:** because the engine links into the Rust process, `sentry-native`'s signal handlers must be gone — Rust owns the single handler.
- **Scope on crash events:** the out-of-process reporter does **not** see the app's scope by default; enable `sentry-rust-minidump`'s `ipc` feature (or sync over the minidumper IPC) so crash events still carry tags/breadcrumbs (e.g. the in-flight IIIF URI).

**`capture_image_error` — DECIDED (Ivan, 2026-06-22): surface the context across the seam to Rust.** Those 8 engine call sites are *handled* C++ exceptions (decode/convert/write), not crashes, and the rich context — the `ImageContext` from `populate_from_image` (dims/channels/bps/colorspace/ICC/orientation + input file + size), the `phase`, and the exception message — exists only inside the engine. The engine **stops calling `sentry-native` directly**; instead it **emits that context across the FFI on the error path**, so the Rust shell has everything it needs and owns the actual reporting (`sentry::capture_event` with the searchable tags + the structured "Image" context, mirroring today's event shape). This keeps one SDK and is fully DRY.

Seam shape (additive, small — analogous to the Phase A `OutputSink` callback): a flat C struct `SipiImageError { const char* phase; const char* message; const char* input_file; const char* output_format; const char* colorspace; const char* icc_profile_type; const char* orientation; uint64_t width, height, channels, bps, file_size_bytes; }` plus a nullable reporter callback `typedef void (*SipiReportErrorFn)(void* ctx, const SipiImageError* err);` carried on `SipiServeRequest` (`report_error` + `report_ctx`). At each catch site `build_image_response` flattens the `SipiImage`/`ImageContext` into the struct and invokes the callback **before** returning its `SipiStatus` — decision #8 stays intact (failures remain clean status codes; the report is a side-channel, never a body). `request_uri` is already held by the Rust edge, so it is attached shell-side rather than threaded down. The engine then links **no** Sentry SDK; `populate_from_image` / `format_type_to_string` stay engine-side (they only flatten into the struct). The CLI convert path (`sipi_cli_main`, still C++) keeps the same struct emitted to a CLI-side reporter (or logs) — resolve in the CLI slice.

**Debug symbols.** `sentry-native`'s libbacktrace symbolicated client-side; minidumps symbolicate **server-side** from uploaded debug files. SIPI already extracts `.debug` via `just bazel-docker-extract-debug` and uploads with `sentry-cli debug-files upload` — reuse it; confirm the artifact format suits the minidump path.

**Container lifecycle — PID 1 + the upload-before-restart race.** SIPI runs in Docker on `@distroless_base` with **`tini` already PID 1** (`src/BUILD.bazel:940`: `["/usr/bin/tini","--","/sbin/sipi"]`, **no `-g`** — good; `-g` would kill the reporter's process group). tini reaps zombies + forwards SIGTERM. The out-of-process model adds a requirement tini does not satisfy on its own: **the reporter must finish writing *and uploading* the minidump before the container exits**, else Docker restarts and the in-flight upload is lost. The race is real:
- **Topology (decided): `tini → sipi-app → sipi-reporter (child)`** — the `sentry-rust-minidump` default. On crash the reporter is orphaned to tini; tini exits as soon as its *own* child (the app) exits and will **not** wait for the orphan. So real-time upload holds **only if the app blocks until the upload completes** — minidumper's `request_dump` blocks until the dump is *written*; whether `sentry-rust-minidump` also blocks through *upload* is the thing to verify.
- **Fallback (decided): NOT a supervisor — upload the dump on next start.** A supervisor topology is rejected as over-engineering. If the app does not block through upload, the minidump is persisted to a restart-surviving path and **flushed on the next startup** — exactly how `sentry-native` works today (it writes to its database run-dir and sends unsent crashes on the next `sentry_init`), and that mechanism is already known-good in the DaSCH deployment. The out-of-process reporter is therefore a real-time *improvement*; deferred-on-restart upload is the acceptable floor, never a lost dump. Implementation: configure the minidump directory on a restart-surviving path (mirroring today's `/tmp/.sentry-native`) and have the Rust shell scan + upload any leftover dumps at startup.
- **Container specifics to verify:** the reporter reads the crashed process's memory via `ptrace`/`process_vm_readv` — works within one PID namespace but needs `ptrace_scope`/`CAP_SYS_PTRACE` not to be dropped; the IPC Unix-domain socket needs a writable path (`/tmp` is already writable — `sentry-native` used `/tmp/.sentry-native`).

Net: this cleanly splits the observability stack — **Sentry = crash/panic reporting + engine-surfaced handled image errors; OTLP/Grafana = traces, RED metrics, structured logs.** (Versions as of 2026-06: `sentry` 0.48.x, `crash-handler` 0.6.x, `sentry-rust-minidump` 0.16.x.)

Debug-symbol upload (`just bazel-docker-extract-debug` + `sentry-cli debug-files upload`) still yields server-side-symbolicated crash reports. `SIPI_SENTRY_{DSN,RELEASE,ENVIRONMENT}` honoured; release = stamped version; `traces_sample_rate = 0.1`.
- **Big-bang mitigation:** canary the Rust binary (one replica / small traffic %) with a **parity SLO** (image-byte equality via approval goldens + error-rate & p99 within an agreed band) and a **defined abort threshold** before the `transport/` delete commit; rollback = revert the cutover commit.

## Phase T — preflight / route extensibility trait (SIPI as a library)

**Goal:** turn the request-shaping policy Lua owns today — `pre_flight`, `file_pre_flight`, and configured custom routes — into **Rust traits a downstream crate implements**, so SIPI can be consumed **as a library**: a user's own crate owns `main`, depends on the `sipi` library crate, and injects its own policy. The C++ Lua runtime stays the **default** implementation; nobody is forced off Lua.

**Why a phase of its own (between C and D+):** it depends on Phase C (the Rust shell + the lib/bin split, decision #9) but is **independent of** the D+ Lua→mlua reimplementation. It is purely additive — it changes *who can supply* preflight/route logic, not *what Lua does*. Honour [[lua_for_request_shaping_only]] and [[sipi_future_preflight_trait_extension]].

**Why it needs no earlier seam change:** decision #8/#9 — preflight is already a discrete, orchestrated step with a pure data contract (the `PreflightDecision` value type: a permission enum + an open kv map), decoupled from the serve path (`sipi_serve_image` never calls preflight; the shell threads preflight outputs in as inputs). B-L already modelled `build_preflight`'s return as that clean value type, so the Rust trait return is a 1:1 port.

### Design

```rust
// Returned by the trait; 1:1 with the C++ PreflightDecision (B-L).
pub struct PreflightDecision { pub permission: Permission, pub kv: Vec<(String, String)> }

pub trait PreFlight: Send + Sync {
    fn pre_flight(&self, prefix: &str, identifier: &str, req: &Request) -> PreflightDecision;
    fn file_pre_flight(&self, filepath: &str, req: &Request) -> PreflightDecision;
}

// Configured custom routes (the script_handler analogue).
pub trait RouteHandler: Send + Sync {
    fn handle(&self, req: &Request, resp: &mut Response);
}
```

- **Default impl wraps the C++ Lua FFI.** `LuaPreFlight` forwards `pre_flight`/`file_pre_flight` to `sipi_preflight` / `sipi_file_preflight`; the default route handler forwards to `sipi_run_lua_route` (Phase C). The shell's preflight step becomes `self.preflight.pre_flight(...)` with `LuaPreFlight` as the default provider — the existing behaviour, now behind a trait object.
- **A user crate provides its own impl** (`impl PreFlight for MyPolicy`), owns `main`, depends on `sipi`, and passes its provider into `sipi::run(config.with_preflight(MyPolicy))`. No Lua, no fork.
- **Scope: preflight + custom routes only.** Config parsing (the `config.*` surface) is **not** trait-ified — it stays config (the `sipi.config.lua` / `SipiServerConfig` surface).

### Steps

1. Define `PreFlight` / `RouteHandler` traits + `PreflightDecision` / `Request` / `Response` Rust types (port the B-L `PreflightDecision`).
2. `LuaPreFlight` (+ default route handler) wrapping the C++ FFI; wire as the default provider in `sipi::run`.
3. Expose provider injection on the `sipi` library API (`ServerConfig::with_preflight` / `with_route_handler`); the default binary uses the Lua providers.
4. Example downstream crate + docs: a user crate implementing `PreFlight` in Rust, depending on `sipi`.

### Exit criteria (Phase T)

- A downstream crate can replace `pre_flight` / `file_pre_flight` (and custom routes) with a Rust impl, with SIPI as a library dependency, **without forking SIPI**.
- The default (Lua) path is byte-for-byte unchanged; existing user Lua scripts run untouched (no migration).
- e2e: the default Lua provider passes the full preflight/route suite; an example Rust provider passes a parity test.

## Risks and mitigations

| Risk | Severity | Mitigation |
|------|----------|------------|
| FFI seam can't express real responses (Range/206, `Set-Cookie`×N, `Retry-After`, framing) | High | **Resolved as-built:** streamed `SipiResponse` with **two** body modes (`send_file` known-length / `write` unknown-length) + status/header/cancel callbacks; framing is the transport's, per HTTP version. Exercised against the e2e suite before Rust. |
| C++ exception unwinding across `extern "C"` (UB) | High | `sipi_guard` catch-all → 500 at every entry; B exit gate. **Note: contains exceptions, not crashes** (see next row). |
| **Codec crash (SIGSEGV/SIGBUS) on a malformed image takes the single process down** | High | **Prevention not solved by the strangler** — `catch(...)` can't catch hardware faults; isolation would need out-of-process decode (rejected) or a sandbox. Stays the C++ engine-hardening backlog (category D: DEV-6063…6075). **Reporting IS in scope (Phase C):** an out-of-process minidump reporter (the `sentry` crate + `crash-handler`/`minidumper`) replaces `sentry-native`'s in-process capture, so the crash still lands a symbolicated Sentry event — see §Crash & error reporting. Distinguish *prevent* (out of scope) from *report* (in scope). |
| Lua FFI inherits the `LuaServer`↔`Connection` coupling | High | **Re-sequenced:** Phase B-L does the `request_context` decoupling **before** any Lua FFI, so `lua` is connection-less and `//src/ffi` stays transport-free. No opaque-handle shim. |
| Preflight map / `restrict` flow lost across the seam | High | `sipi_preflight` returns a permission *type* + kv channel; `restricted_size`/`watermark_path` thread into `sipi_serve_image`; info.json auth-service block + restricted previews covered by e2e (B-L). |

| Content-Range vs Content-Length divergence on out-of-range requests | Low | **Fixed in `decide_serve_file`:** `end` clamped to `fsize-1` so Content-Range's last-byte-pos always equals the delivered length (RFC-correct; legacy let them diverge). Unit-tested. |
