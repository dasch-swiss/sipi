## 1. The reframe (2026-06-23, Ivan)

Phase C's terminal strategy — this supersedes the "canary into production, then delete the transport" framing in `01`:

1. **There is no incremental production deploy.** SIPI is **not** deployed in a half-cutover state. The deploy gate (reshaped 2026-07-10 — full criteria in §9) is **Phase C complete + differential parity proven** (incl. JWT via the step-9 response-sink fix) **+ crash reporting and basic OTLP visibility migrated + docs cleaned up + a staging soak**. (The mdBook migration, the full metric-value parity restoration, and D+ (mlua/codec) all proceed *after* deploy, the normal strangler way; **none** is a deploy prerequisite. The former Phase T public-API trait is **dropped**, not deferred — ADR-0017 / §10.)

2. **The retained C++ server is only worth keeping if it is a *live differential oracle*.** Right now it is not: the e2e suite (session 4, `2aac0b9`) spawns **only** the Rust shell, so we test new-against-new and call it parity. The C++ code is a *historical* reference in git, not a running comparison target. The benefit of delaying the transport delete (`01` Item 2b) is **entirely** the differential-testing value — so we must actually capture it.

**Amendment (2026-07-15, Ivan) — deploy on Rust, retain the oracle, defer the delete.** The transport delete is no longer a deploy prerequisite at all. **Deploy the Rust binary and keep the C++ transport in-tree** (buildable, not deployed) as the ongoing differential oracle — it costs a flat, cache-warm maintenance tax and nothing at runtime. This removes the *irreversible* step from the critical path and lets the oracle keep earning its keep after deploy. **Sunset trigger for the C++ oracle** (retire it — step 13 — at whichever comes first): (a) intentional transport divergences come to dominate the §5 allowlist (the oracle tests nothing on the allowlisted surface, so the post-deploy trait/TOML/Lua-deprecation work erodes its coverage), or (b) the first post-deploy change that forces editing the C++ transport *itself* just to keep it compiling. Naming the trigger is what keeps "retain it" consistent with a repo that otherwise deletes aggressively. The Docker entrypoint already points at `//src/cli-rs:sipi` ([sipi#721](https://github.com/dasch-swiss/sipi/pull/721)); step 13 is now purely the C++-source removal.

**Consequences (this plan's spine):**

- **Item 2b (delete `shttps/transport` + `SipiHttpServer`) moves OUT of the deploy gate** into the post-deploy tail (per the 2026-07-15 amendment above), gated on the sunset trigger — not "dead-last before deploy" but "later, when the oracle stops paying for itself." The deploy ships the Rust binary with the C++ transport retained.
- **The safety net during the remaining pre-deploy steps is differential testing against the retained C++ oracle**, not a production canary. There is no traffic-split canary at all; the final pre-deploy check is a staging soak + a narrow transport-layer benchmark, then deploy-and-monitor (§9, step 14).
- **The e2e suite is treated as incomplete, not as the definition of parity.** We characterize the full C++ behaviour surface, add the missing tests to **both** binaries (they pass on C++ = oracle; they expose Rust gaps), then drive Rust to match.
- The `01` "prod canary as the Phase C exit gate" framing is **superseded** by this document.

## 5. Known-intentional divergences — the differential-harness allowlist

Where Rust ≠ C++ **by design** — the diff harness treats these as expected; everything else that differs is a test failure.

1. **`/metrics` removed** — OTLP replaces the Prometheus scrape; Rust has no route.
2. **Observability stack** — OTLP + `RUST_LOG`/EnvFilter vs C++ syslog + sentry-native; `/health` version from `SIPI_SENTRY_RELEASE`/`CARGO_PKG_VERSION` vs `SipiVersion`.
3. **TLS at Traefik** — Rust serves plain HTTP only; `--sslport`/`--sslcert`/`--sslkey` parse but are inert; no HTTPS listener.
4. **Pool backpressure** — Rust semaphore shed-load → 503 `Retry-After:1` vs C++ thread-per-connection socket queue (`Retry-After:5`).
5. **Error body** — Rust bare status, empty body; C++ `send_error` echoes `Bad Request: <msg>`. The no-internal-path-leak guarantee holds on both (DEV-6062).
6. **Transport framing** — hyper `Server`/`Date`/`Connection` headers + native chunked vs shttps; no config-driven keep-alive idle timeout (tokio is async — §3 P2).
7. **`tmpdir`/`max_temp_file_age`** — Rust spools to system-TMPDIR `NamedTempFile`, no age reaper.
8. **Not-ready 503** — without `--config` the Rust shell serves routes 503 + `/health` 200; C++ requires `--config`.
9. **Forwarded-header derivation** — the divergence is **scheme on the image/info path** and **host source everywhere**, *not* the 303 scheme (corrected 2026-07-10 against source):
    - **Canonical-URL / `Link` scheme + info.json `id` scheme:** the C++ *image* path pins `req.forwarded_proto = nullptr` (`SipiHttpServer.cpp` serve_iiif) → always `http://`; Rust derives it from `X-Forwarded-Proto`. Divergence — Rust's XFP scheme is the pinned contract; the harness tolerates it (existing `Allow::Xfp` cases mask `/id`).
    - **Host source (all paths, incl. info/knora/303):** C++ uses the raw `Host` header (`Connection` `_host`; `X-Forwarded-Host` is never read); Rust prefers `X-Forwarded-Host`, falling back to `Host`. Divergence — Rust's XFH host is the pinned contract.
    - **303 redirect scheme — NOT a divergence:** C++ `serve_redirect` (`SipiHttpServer.cpp:506-531`) derives the scheme from `conn.secure()`, which honours `X-Forwarded-Proto: https` (`Connection.cpp:886-889`) — same as Rust. Both agree; nothing to allowlist on the 303 scheme. (The earlier "C++ hardcodes `http://` for the 303" claim was wrong — that `forwarded_proto = nullptr` belongs to the unrelated image-serve FFI struct at `SipiHttpServer.cpp:1300`.)
10. **Malformed-identifier CR/LF → 400** — a bare-identifier 303 request whose `{id}` contains CR/LF: Rust rejects (400, header-injection guard); C++ strips the CR/LF and sends the 303. Rust's 400 is the contract; the harness expects 400 on Rust, 303 on C++. Real identifiers never contain CR/LF, so normal traffic is unaffected.
11. **info.json `ACAO:*` + the oracle's stray `ACAC:true`** — the oracle overwrites `ACAO` to `*` on info.json (`SipiHttpServer.cpp:768`) while leaving the engine's `ACAC:true` in place (an illegal-but-harmless pairing — browsers ignore credentials with `*`). Rust emits `ACAO:*` on info.json (it is public, no credentialed CORS needed); the harness tolerates the oracle's stray `ACAC:true`.
12. **`health` verb CLI surface** — `health` is parsed by Rust **clap**, not C++ **CLI11** (the only offline verb that is). The happy path (`health --port N` → exit 0/1) matches `cmd_health`; the error/help surface (`--help` layout, bad-flag message, exit code on bad input) differs from the other offline verbs by design. Intentional divergence (like the `--adminuser` env typo) — the harness asserts the happy path, not the clap-vs-CLI11 error text.
13. **`%252F` double-decode** (DEV-6700, resolved 2026-07-11) — `/unit%252Flena512.jp2/…`: the oracle double-decodes (`%252F → %2F → /`) and serves the file (200); the Rust shell decodes once, so the path separator never materialises and the identifier 404s. Rust's single-decode is the safer contract (no double-decoded traversal foot-gun). Confirmed safe against real traffic by checking `dsp-api`/`ops-deploy` directly: Knora asset IDs are base62-encoded UUIDs (`[a-zA-Z0-9-_]{11}-{11}`, no `/` in the alphabet at all), dsp-api builds SIPI URLs via raw string interpolation without even single-encoding the identifier, and Traefik's `allowEncodedSlash`/`allowEncodedPercent` entrypoint settings exist for unrelated reasons (an internal `/store` admin-route block-rule bypass concern, and gravsearch's literal `%25`) — not image identifiers, and don't themselves decode anything. No legitimate identifier is ever double-encoded.

**Always-ignore (transport noise):** `date`, `server`, `connection`, `keep-alive`, `transfer-encoding`, and `content-length` when one side streams chunked.

**NOT divergences — the harness must ASSERT these** (Rust must match C++): the CORS credentialed-request contract on the image/file/preflight routes (§6 H), and the genuine bugs in §6 (`/file` UTF-8 Content-Disposition, favicon). *(The `Link` scheme, info/knora host, and 303 CRLF are intentional XFP/reject divergences — items #9/#10 above, not bugs to fix.)*

### H — CORS: echo Origin + credentials (required)

SIPI is a public, internet-facing IIIF server, so an origin **allowlist is not possible** — the set of legitimate front-end origins is open. The oracle's CORS is **route-dependent** (verified): `Connection.cpp:393-394` sets `ACAO:<origin>` + `Access-Control-Allow-Credentials: true` on *any* request carrying an `Origin`; the **info.json** handler then overwrites `ACAO` to `*` (`SipiHttpServer.cpp:768`), leaving the (now stray) `ACAC:true`. So the contract is per-route:

- **Image / file / preflight → echo `Origin` + `Access-Control-Allow-Credentials: true`.** Mandatory for cookie auth — without the credentials header the browser withholds the DSP/Knora session cookie cross-origin and SIPI's preflight has nothing to authenticate by. The Rust shell currently omits it (`routes.rs:153-158`, `430-443`) — **that is the fix.**
- **info.json → `ACAO:*`** (match the oracle, `SipiHttpServer.cpp:768` / `routes.rs:729`). info.json is public (it carries the auth-service block *for everyone*), so it needs no credentialed CORS. The oracle's stray `ACAC:true` there is harmless (browsers ignore credentials with `*`) — **allowlist it** (§5 #11); do **not** echo `Origin` on info.json, and do not present "echo Origin" as parity (the oracle ships `*`).
- **OPTIONS preflight** — the oracle (`Connection.cpp:411-414`) emits `Allow-Methods: GET, POST, PUT, DELETE` gated on Origin + Access-Control-Request-Method + -Headers all present; today's Rust is an unconditional `204` + `GET, HEAD, OPTIONS` (`routes.rs:430-443`). Advertise the methods the routes use **including POST** (upload), matching the oracle's list; the `204`-vs-gating shape is allowlistable if behaviourally equivalent.

**Not a single global `CorsLayer`.** The policy is route-dependent (echo on image/file, `*` on info.json) and `*` is incompatible with `allow_credentials(true)`, so one global `mirror_request()`+credentials layer cannot express it. Keep CORS **per-handler** (as the shell does today), adding the credentials header on the image/file/preflight paths only. (DEV-6061 tracked an origin allowlist; that premise does not apply to a public server.)

### 7.5 CLI / clap organization (A0 = full overrides)

Designed from a clap-v4 best-practices research pass (Context7 canonical docs + config/CLI-precedence patterns + a grounding pass over the SIPI flag inventory and the `SipiConf` setter surface, 2026-06-23). Scope is the **`server` arm only** — the offline verbs are out of scope (see below).

#### Module structure — `cli-rs` (bin) + `server-rs` (lib), mirroring C++ `cli` + the server

**The Rust shell is two crates** — the monolithic `server-rs` splits into a library + a binary. This mirrors the C++ structure *and* makes decision #9's library boundary physical:

| Rust crate | Role | Mirrors (C++) | Bazel |
|---|---|---|---|
| **`src/server-rs/`** | the **`sipi` library** — the axum server shell: `lib.rs` (`sipi::run`), routing, IIIF, info/knora assembly, the streaming `SipiResponse` sink, the **server-seam FFI** (`sipi_init` / `sipi_serve_*` / `sipi_run_lua_route` / preflight / metrics / config getters), config-override application, OTel. The reusable thing a downstream crate depends on. | `SipiHttpServer` + `shttps/transport` (the server the strangler replaces) | `//src/server-rs:lib` (rust_library, crate `sipi`) |
| **`src/cli-rs/`** | the **default binary / entrypoint** — owns `main` + the thin clap dispatch (`server` → `server-rs`'s `sipi::run`; **`health` → a Rust-native loopback probe** (no FFI); every other argv → `sipi_cli_main` via its **own** `extern "C"` binding) + the `server` command's clap (`commands/server/`). Deps `//src/server-rs:lib` (server verb) **and** `//src/cli:cli_app` (`sipi_cli_main`; `health` needs neither). | `src/cli/` (`cli_app.cpp` + the offline verbs behind `sipi_cli_main`, `sipi.cpp` thin main) | `//src/cli-rs:sipi` (rust_binary) |

This is the **two-crate realization of decision #9** (`01`): `server-rs` *is* the `sipi` library; `cli-rs` is the stock binary that wraps it. A downstream user crate consumes `//src/server-rs:lib` and supplies its own `main` exactly as `cli-rs` does. The e2e `SIPI_BIN` retargets to `//src/cli-rs:sipi` — and the differential harness reads cleanly: subject `//src/cli-rs:sipi` vs reference `//src/cli:sipi` (same target name, the package names the language).

**FFI placement — each crate binds the FFI it calls; neither routes through the other.** The two C-ABI surfaces are disjoint: `cli-rs` calls only `sipi_cli_main` (offline verbs); `server-rs` calls only the server seam (`sipi_init` / `sipi_serve_*` / `sipi_run_lua_route` / preflight / metrics / config getters). So `cli-rs` declares its **own** `extern "C" { fn sipi_cli_main(argc, argv) -> c_int; }` and calls it directly — it does **not** reach `sipi_cli_main` through `server-rs`. The `cli-rs → server-rs` edge exists **only** for the `server` verb (`sipi::run`); `server-rs` never sees offline args. Bazel: `cli-rs` deps both `//src/server-rs:lib` and `//src/cli:cli_app`; `server-rs` deps `//src/ffi:sipi_ffi` + `//src:engine`; the C++ engine is linked **once** into the final binary. No shared FFI-sys crate — the surfaces don't overlap (extract one only if they ever do). The clap→override mapping: `cli-rs` parses `ServerArgs` → a **Rust-native `ServerOverrides`** (Option fields, exposed by `server-rs`); `server-rs` converts it to the `#[repr(C)] SipiServerConfig` internally for `sipi_init` (the C-repr struct stays private to the library).

#### Scoping — clap reorganizes `server`, not the whole CLI

Keep the hand-rolled argv scan (today `run()` at `lib.rs:68`; it moves to **`cli-rs/src/main.rs`** with the split) that routes `server` → `server-rs`'s `sipi::run`, **`health` → a Rust-native probe** (§7.6), and **every other argv → `sipi_cli_main` verbatim** (cli-rs's own `extern "C"` binding — not through `server-rs`). Do **not** introduce a top-level clap `Parser` owning all verbs: the offline verbs (`convert`/`verify`/`query`/`compare`) must reach the C++ CLI11 parser byte-identically — a Rust clap top-level would diverge on `--help`/`--version`/error text and break the differential harness. The clap reorg touches only the `server` arm.

#### Module layout (two crates)

Each Rust-native verb is its own module under **`cli-rs/src/commands/`** (mirroring the C++ `src/cli/commands/` convention — `health`, `verify`, `convert_*`), so a reader discovers every command at a glance. **A command owns its own args** — a small verb is a single file (`commands/health.rs`); a big one is a folder (`commands/server/`) holding its handler plus an `args/` submodule of per-domain `#[derive(Args)]` groups composed via `#[command(flatten)]` (each with a `#[command(next_help_heading = "...")]` so `--help` renders sectioned). There is **no top-level `args/`** — args never float free of the command they belong to, and a future offline verb that grows its own arg set gets its own `commands/<verb>/args/`. clap is layout-agnostic (`flatten` composes groups from any module), so this is purely an organization choice. The `server-rs` library owns the shell + FFI:

```
src/server-rs/src/            # the `sipi` library  (//src/server-rs:lib, crate sipi)
  lib.rs                      #   sipi::run — sipi_init install + axum serve
  routes.rs iiif.rs info.rs sink.rs   #   the shell
  ffi.rs                      #   server-seam FFI bindings (sipi_init / serve_* / run_lua_route / preflight / metrics)
  config.rs                   #   pub ServerOverrides (Rust-native) + repr(C) SipiServerConfig (private)

src/cli-rs/src/               # the default binary / entrypoint  (//src/cli-rs:sipi)
  main.rs                     #   entrypoint: scan the verb → dispatch (server/health → commands::*; else → sipi_cli_main)
  ffi.rs                      #   extern "C" sipi_cli_main — the ONLY FFI cli-rs binds
```

Only `ServerArgs` is `pub` in `cli-rs`; group structs are crate-internal. The `From<&ServerArgs> for ServerOverrides` mapping lives in `cli-rs/src/commands/server/` (it knows `ServerArgs`); the `ServerOverrides` type + the `repr(C) SipiServerConfig` live in `server-rs/config.rs` (next to the FFI). `--config` is bootstrap (it *selects* the base Lua config the overrides layer onto), not an override. Sentry flags stay **out** of `ServerArgs` — they are top-level env reads in C++ (`SIPI_SENTRY_*`) applying to all verbs; the shell already reads `SIPI_SENTRY_RELEASE` directly (`lib.rs:316`). Keep them as env reads in telemetry/Sentry init.

#### Precedence — `config (base) < env var < CLI flag` (verified against C++)

**The C++ hierarchy is `config < env < CLI`, uniform across (essentially) all `server` flags** — verified in `cli_app.cpp:1117-1232`:
- The Lua config loads as the **base** — but only when `--config`/`SIPI_CONFIGFILE` is set (`1128-1133`); without a config file the flag/env/default values apply directly (no Lua base).
- Per flag, the config value is overridden **when `user_set(flag)`** (`1141`/`1146`/…). `user_set` = `option != nullptr && !option->empty()` (`1118-1121`); CLI11 populates an option from its `->envname` during parse, so **`empty()` is false for an env-provided value too** → env overrides config. The code comment at `1136` is explicit: *"check for all commandline/environment variables and update sipiConf."* Within CLI11 a CLI value beats the env fallback. Net: **config → env → CLI.**
- Every server flag carries `->envname` (`cli_app.cpp:1640-1748`), so this is a single uniform gate, not a per-flag special case.

**The clap design reproduces this exactly.** Every overridable field is `Option<T>` with **NO `default_value`** (a clap default would silently clobber the config value). `None` (set by neither CLI nor env) → fall through to the Lua config; clap's fixed **`CLI > env`** ordering then matches C++. So the Rust effective order is `config < env < CLI`, identical to the oracle — the `Option<T>`-`None`-means-config rule *is* the Rust analog of the `user_set` gate, and **no `ValueSource` threading is needed** (we never set defaults). A config crate (figment/config-rs) is **rejected for the Lua path** — with a Lua base, Rust doesn't own the merged config (the Lua VM does), so a crate would force a duplicate Rust schema for zero benefit; hand-rolling is less code. (For a `.toml` base (**M5**) Rust *does* own the merge — even there, hand-rolling the small `TOML < env < CLI` merge beats a crate.)

```rust
#[derive(Args, Debug)]
#[command(next_help_heading = "Network")]
pub struct NetworkArgs {
    #[arg(long, env = "SIPI_SERVERPORT", value_name = "PORT")] pub serverport: Option<u16>,
    #[arg(long, env = "SIPI_SSLPORT",   value_name = "PORT")] pub sslport:    Option<u16>,
    #[arg(long, env = "SIPI_HOSTNAME",  value_name = "HOST")] pub hostname:   Option<String>,
    #[arg(long, env = "SIPI_KEEPALIVE", value_name = "SECS")] pub keepalive:  Option<i32>,
}
```

Deprecated aliases (`--cachedir`/`--cachesize`/`--cachenfiles`) are separate `hide = true` fields collapsed in `From` (they differ in hyphen-shape from the canonical names, so `visible_alias` doesn't apply); they hit the same setter.

#### Env-var map (C++ `->envname` → clap `env =`)

1:1 port (clap has no `env_prefix`). **Verified: all 44 server options carry `->envname` in C++** (`cli_app.cpp:1638-1748`), so the env layer is uniform, not partial. Full table in the source design; spans Network / Concurrency / Limits / Paths / Cache / Rate-limiting / TLS&Auth / Knora / Logging.

> **Sentry is outside this hierarchy.** `SIPI_SENTRY_{DSN,RELEASE,ENVIRONMENT}` are read by C++ both as **top-level CLI flags** `--sentry-*` (`cli_app.cpp:807-811`, apply to *all* verbs) **and** directly via `getenv` (`659-661`); they are env-driven, not config-file-layered. The Rust shell reads them from **env only** (`lib.rs:316` + Sentry init). Minor parity gap: C++ also accepts `--sentry-*` on the CLI; the Rust shell does not. **Decision: env-only is fine** (these are deploy-time secrets/identity set via env in every DSP deployment) — pin it as a documented divergence rather than adding the CLI flags.

> **The `SIPI_ADMIINUSER` typo (`cli_app.cpp:1739`).** C++ binds `--adminuser` to the **misspelled** `SIPI_ADMIINUSER` (double-I). **Fix it — bind clap to the correct `SIPI_ADMINUSER`** (a latent bug nobody can intentionally rely on). #### The FFI override channel — `SipiServerConfig`

Replace the null at `ffi.rs:413` and make the incomplete `SipiServerConfig` at `sipi_ffi.h:198` concrete. Presence-flag-per-field encodes the Rust `Option<T>` in C (no `Option`): **null pointer = absent for strings**, **`has_<field>: c_int` for scalars** (consistent with the seam's existing "null = absent" idiom, e.g. `range` in `sipi_serve_file`). The flow across the crate boundary: `cli-rs` maps clap `ServerArgs` → the Rust-native `ServerOverrides` (Option fields); `server-rs/config.rs` converts that into an `OverridesHolder` that owns the `CString`s + the `repr(C) SipiServerConfig` so the pointers outlive the synchronous `sipi_init` call (seam contract: caller-owned inputs outlive the call). The `repr(C)` struct never leaves `server-rs`.

```rust
#[repr(C)]
pub struct SipiServerConfig {           // mirrors sipi_ffi.h; applied over the parsed Lua config
    pub serverport: c_int, pub has_serverport: c_int,   // scalars: paired has_ flag
    pub scriptdir:  *const c_char,                      // strings: null = absent (a FORWARDED flag)
    pub maxpost:    *const c_char,                      // sized strings ("300M") parsed engine-side
    pub imgroot:    *const c_char,
    pub cache_dir:  *const c_char, pub cache_size: *const c_char, pub cache_nfiles: c_int, pub has_cache_nfiles: c_int,
    // ... one field (+ has_ for scalars) per forwarded flag; subdirexcludes = *const *const c_char + len ...
}
// in server-rs/config.rs: cli-rs hands over a ServerOverrides (Option fields); the holder owns the C storage.
pub struct ServerOverrides { pub serverport: Option<u16>, pub imgroot: Option<String>, /* … one Option per FORWARDED flag (not hostname — that's parse-only/dead) … */ }
pub struct OverridesHolder { _strings: Vec<CString>, _vecs: Vec<Vec<*const c_char>>, pub cfg: SipiServerConfig }
impl OverridesHolder { pub fn from_overrides(o: &ServerOverrides) -> Self { /* Some(_) → ptr + has_ flag; aliases collapse */ } }
```

C++ side: in `sipi_init`, **after** `conf = SipiConf(luacfg)` (`cli_app.cpp:509`) and **before** the cache/rate-limiter/memory-budget are constructed from `conf` (`:511+`), apply each present override via the existing setters (`setPort`/`setImgRoot`/`setMaxPostSize`/`setJwtSecret`/`setCacheDir`/… — forwarded flags only) — the same `if (user_set) conf.setX(...)` block `run_server` uses today (`cli_app.cpp:1138-1486`). **Ordering is load-bearing:** overrides before service construction, or an overridden `--cache-size`/`--rate-limit-*` won't take effect.

`--drain-timeout` is **Rust-owned** (`lib.rs:146`, the graceful-drain deadline) and stays Rust-side — not in the override struct.

**Single-source the `SipiServerConfig` layout.** It is defined twice — the `#[repr(C)]` in Rust `config.rs` and the concrete `struct` in `sipi_ffi.h` (today an opaque incomplete type at `:198`). Field order, `has_` flags, pointer widths, and padding must match by hand, or it is silent UB on drift. Guard it: a Rust offset/`size_of` test against the header **plus** a C++ `static_assert(sizeof(SipiServerConfig) == …)` — **decided (Ivan): the offset/`size_of` test, not bindgen** (the seam is small and hand-mirrored on purpose), with a lock-step comment in both files. **This guard decision is already recorded as comments** at both sites (`sipi_ffi.h:198` + `server-rs/config.rs`, landed in #692), awaiting M4's concrete struct.

#### Forward vs parse-only — the dead-transport question (OPEN, §6)

All 44 server options **parse on both binaries** (parity), but only the **engine-behaviour** set is **forwarded** into the override struct. Forwarding a transport flag the post-cutover engine no longer reads buys nothing and misleads future readers. The split:

- **Engine-behaviour → FORWARD:** `serverport` (engine's own view), `imgroot`, `scriptdir`, `initscript`, `tmpdir`, `maxtmpage`, `jwtkey`, `adminuser`, `adminpasswd`, `cache-*`, `rate-limit-*`, `max-decode-memory`, `decode-memory-mode`, `max-pixel-limit`, `maxpost`, `pathprefix`/`subdirlevels`/`subdirexcludes`, `thumbsize`, `loglevel`, `knorapath`, `knoraport`.
- **`docroot` / `wwwroute` → FORWARD.** Cluster C reimplements the `/server` fileserver in Rust, which needs the docroot + wwwroute config; the Rust fileserver reads them (with the CLI override applied).
- **Genuinely dead (Rust owns the transport) → PARSE-ONLY, accept-and-ignore with a doc comment:** `sslport`, `sslcert`, `sslkey` (TLS at Traefik), `keepalive`, `max-waiting`, `queue-timeout` (Rust semaphore concurrency model), `hostname` (Rust derives from X-Forwarded-Host).

### 7.6 Environment-variable & config surface

SIPI's env/config inputs span three tiers; all must survive the cutover. Verified against the worktree + `dsp-api/sipi/` + `ops-deploy/roles/dsp-deploy/`.

**Tier 1 — C++ binary `SIPI_*` (CLI11 `envname`).** All 44 `server` options carry `->envname` (`cli_app.cpp:1638-1748`); precedence `config < env < CLI` (§7.5). **Prod sets none of them** — the container launches `server --config=/sipi/config/sipi.prod-config.lua` and every tunable comes from the templated Lua config (`ops-deploy .../sipi.prod-config.lua.j2`). So this tier is a *capability* the clap must reproduce (A0 — for the test suite + general parity), not a prod dependency.

**Tier 2 — Sentry.** `SIPI_SENTRY_{DSN,RELEASE,ENVIRONMENT}` — set in the prod container env. C++ reads all three via `getenv` (`cli_app.cpp:659-661`) and inits sentry-native. The Rust shell reads `RELEASE`/`ENVIRONMENT` (`lib.rs:316`, `telemetry.rs:102-109`) for the `/health` version + OTel resource, but **not `DSN`** → R1.

**Tier 3 — Lua-consumed (`os.getenv` in dsp-api scripts).** Read by the Lua VM behind the FFI, **not** the binary. SIPI's own bundled Lua has none; these live in dsp-api's `env.lua`/`util.lua` (shipped into `knora-sipi`) and are set in the prod container env:

| Var | Lua use | Fallback |
|---|---|---|
| `KNORA_WEBAPI_KNORA_API_EXTERNAL_HOST` / `_PORT` | JWT `iss` + auth cookie name (`env.lua`) | **none → `send_error(500)`** |
| `SIPI_WEBAPI_HOSTNAME` / `_PORT` | dsp-api target for the `/admin/files/` permission call (`util.lua`) | `config.knora_path`/`knora_port` |
| `SIPI_EXTERNAL_PROTOCOL` / `_HOSTNAME` / `_PORT` | external IIIF URL building (`util.lua`) | `'http'` / `config.hostname` / `config.port` |

**These survive the cutover unchanged.** `make_lua_server` (`lua_config.cpp:23-35`) builds each per-request VM via the 4-arg `LuaServer` ctor, which calls `luaL_openlibs` (`LuaServer.cpp:270`) → `os.getenv` is present in every preflight/route VM; the Rust binary inherits the container env, so the reads resolve identically. The cutover must **not** scrub env or sandbox Lua.

**Prod launch (verified).** Container command: `server --config=/sipi/config/sipi.prod-config.lua` (only those two tokens). Docker `HEALTHCHECK`: `/sbin/sipi health --port 1024` — reimplemented as a **Rust-native** `health` verb in `cli-rs` (§7.5), no longer routed to the C++ `sipi_cli_main`. **Risks / harness pins:**
- **R1 — Sentry DSN, server mode (medium; §6, Item 3).** The Rust server path never reads `SIPI_SENTRY_DSN`, so a cutover today loses server-mode Sentry crash reporting (OTel needs `OTEL_EXPORTER_OTLP_ENDPOINT`, absent from the prod env block). Decision in §6.
- **R2 — Lua `os.getenv` survival (low).** Pin: a preflight needing `KNORA_WEBAPI_KNORA_API_EXTERNAL_HOST` succeeds under the Rust binary; unset → 500 (the no-fallback contract). Assert the Rust process never `env_clear`s/sandboxes.

- **`health` verb (Rust-native).** Reimplemented in `cli-rs` (GET `127.0.0.1:<port>/health` → exit 0 on HTTP 200 else 1; std TCP, no FFI), matching `cmd_health` (`src/cli/commands/health.cpp`: 1s connect / 2s total timeout). ## 10. Long-term: runtime-scripting extensibility (evaluate a more approachable language than Lua)

Beyond Phase C/Docs and the D+ tail, the long-term extensibility direction (ADR-0017, amended 2026-07-17 — **supersedes the 2026-06-26 "native-first Rust trait" plan**) is:

- **Request-shaping extensions (the `pre_flight`/`file_pre_flight` auth hooks and custom routes) stay runtime-loaded scripts — no compilation or toolchain required from the author.** The goal is that a **non-technical user** can write and change an extension by editing a script the running server loads, not by compiling anything.
- **Two facts drive this.** (1) **Only DaSCH can compile SIPI** (Kakadu is license-gated), so a compile-time Rust trait has no external audience and forces a full rebuild + redeploy for every policy change. (2) The goal above — extension without a toolchain — is the opposite of a compile-time trait.
- **Evaluate a more approachable scripting language to succeed Lua.** **Roc (roc-lang) is the first candidate**: its platform/application model (Rust/Zig/C host exposes effects + the user's application code) fits "SIPI host exposes `http`/`respond`/… effects + auth logic as the script." **Candidate, not a commitment** — Roc is pre-1.0 with a small ecosystem, so if it does not meet the no-toolchain, approachable-for-non-technical-authors bar, another Lua alternative is chosen. **LLM-assisted authoring is assumed**, which widens the candidate set (familiarity matters less than a clean host-effect boundary + safety) but does **not** relax the no-toolchain constraint.
- **Dropped:** the Rust `pre_flight`/route trait / SIPI-as-library "native-first" direction (former Phase T, DEV-6670). A Rust trait may remain an internal host-dispatch detail, but it is **not** the user-facing extension mechanism.

**Config is separate and unaffected:** TOML config (M5) stays the declarative config surface (serde + toml); it is config, not scripting.

This is a **multi-year, later-stage exploration** — **not** a deploy prerequisite, and not near-term (Roc's maturity puts it at ~2027+). The constraint inherited from ADR-0017: no forced migration off Lua before a stable, prod-proven replacement exists, with a documented migration path. Independent note: the script→dsp-api distributed-tracing gap is **not** solved by the language swap — it needs host-side `traceparent` injection across the seam regardless.
